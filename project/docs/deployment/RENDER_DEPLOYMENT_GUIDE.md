# TrustDrive Render Deployment Guide

## Important architecture decision

Do **not** create this project as a Render **Static Site**. The `frontend/`
application is a Next.js server application: it contains server components,
API routes, authentication, uploads, and the SQLite-backed data layer.

The supported production deployment is:

```text
One Render Docker Web Service
  ├─ Next.js frontend and REST API
  ├─ FastAPI intelligence service
  ├─ DB-backed worker
  └─ One persistent disk containing SQLite and uploads
```

The repository already contains the required files:

- `render.yaml` — Render Blueprint
- `project/infra/docker/Dockerfile.render` — combined production image
- `project/infra/deployment/start-render.sh` — starts Next.js, FastAPI, and worker

The Blueprint uses a persistent `/data` disk so both runtimes use the same
database. Splitting the frontend and backend into separate Render services is
not supported while the Next.js data layer uses SQLite.

## Before deploying

1. Push the repository to GitHub.
2. Confirm these files exist on the selected branch:

   ```text
   render.yaml
   project/infra/docker/Dockerfile.render
   project/infra/deployment/start-render.sh
   frontend/
   backend/
   services/
   ```

3. Make sure `render.yaml` is on the branch you will deploy, normally `master`.
4. Do not commit `.env`, `.env.local`, passwords, API keys, or private files.

## Create the Render service

1. Open [Render](https://render.com/) and sign in with GitHub.
2. Select **New +** → **Blueprint**.
3. Connect the GitHub repository:

   ```text
   samarthdarak24-cpu/we-duo
   ```

4. Select the deployment branch:

   ```text
   master
   ```

5. Render detects `render.yaml`. Click **Apply**.
6. Confirm the service settings:

   | Setting | Value |
   | --- | --- |
   | Service name | `trustdrive` |
   | Type | Web Service |
   | Runtime | Docker |
   | Dockerfile | `./project/infra/docker/Dockerfile.render` |
   | Region | Singapore |
   | Plan | Starter (supports persistent disk) |
   | Port | `10000` |
   | Health check | `/api/v1/health/ready` |
   | Persistent disk | `trustdrive-data` mounted at `/data` |
   | Disk size | 10 GB |

7. Click **Create Blueprint** / **Apply**.

## Required environment variables

The following variables are already defined by `render.yaml`. Review them in
**Render → trustdrive → Environment**.

### Automatically generated by Render

These must remain secret. `generateValue: true` makes Render generate and keep
them across deploys:

| Variable | Purpose |
| --- | --- |
| `JWT_SECRET` | Signs login sessions |
| `TD_SERVICE_TOKEN` | Authenticates internal Next.js ↔ FastAPI requests |
| `DOWNLOAD_SIGNING_SECRET` | Signs private document download links |
| `QR_SIGNING_SECRET` | Signs vehicle QR verification tokens |
| `TD_SHARE_SECRET` | Signs temporary report share tokens |

### Required on first boot

Set these manually in the Render dashboard:

| Variable | Example | Notes |
| --- | --- | --- |
| `ADMIN_EMAIL` | `admin@example.com` | Initial administrator login |
| `ADMIN_PASSWORD` | Use a unique password of at least 8 characters | Never commit this value |

Set them before the first deployment finishes. With `TD_SEED_DEMO=0`, the first
boot creates the administrator from these values and does not create demo
accounts. With `TD_SEED_DEMO=1` it also seeds the labelled synthetic demo
dataset (buyer, seller, vehicles, listings). Use `0` for a real customer
instance and `1` only for a demo or QA deployment.

### Database and runtime variables

These are already configured by `render.yaml`; do not change them unless the
deployment architecture changes:

```env
NODE_ENV=production
TD_ENV=production
PORT=10000
TD_DATA_DIR=/data/trustdrive
TD_DB_FILE=/data/trustdrive/trustdrive.db
TD_DB_URL=sqlite+pysqlite:////data/trustdrive/trustdrive.db
TD_UPLOAD_DIR=/data/trustdrive/uploads
TD_QUARANTINE_DIR=/data/trustdrive/quarantine
TD_CHECKPOINT_DB=/data/trustdrive/langgraph-checkpoints.db
TD_MODEL_DIR=/app/services/ai/shared/models
TD_INTELLIGENCE_URL=http://127.0.0.1:8000
# 1 = seed the labelled synthetic demo dataset; 0 = admin bootstrap only.
TD_SEED_DEMO=1
# Run the DB worker as a FastAPI thread instead of a third Python process.
TD_WORKER_MODE=inline
# On the 512 MB Free plan use Tesseract: a real OCR engine whose CLI process
# peaks at ~30-60 MB. Set rapidocr (or leave auto) on a Starter 2 GB instance.
TD_OCR_PROVIDER=tesseract
# Bound the image sent to OCR and refuse OCR when less than this much memory is
# free (the document stays pending with the honest reason).
TD_OCR_MAX_IMAGE_SIDE=1024
TD_OCR_MIN_FREE_MB=160
TD_LLM_PROVIDER=none
```

`TD_INTELLIGENCE_URL` uses `127.0.0.1` because Next.js and FastAPI run inside
the same Render container. Do not use `localhost:3000` for this variable. Also set
`NEXT_PUBLIC_APP_URL` to your `https://<service>.onrender.com` URL (or leave it
unset to fall back to Render's `RENDER_EXTERNAL_URL`). On Render's `$0` Free
plan without a persistent disk, point `TD_DATA_DIR`, `TD_DB_FILE`, `TD_DB_URL`,
`TD_UPLOAD_DIR`, `TD_QUARANTINE_DIR`, and `TD_CHECKPOINT_DB` under
`/tmp/trustdrive` (accepting that SQLite and uploads reset on every deploy or
spin-down).

### Optional external LLM variables

Leave these empty for the deterministic evidence-only assistant:

```env
TD_LLM_BASE_URL=
TD_LLM_API_KEY=
TD_LLM_MODEL=
```

If using an OpenAI-compatible provider, set all three in the Render dashboard.
Never put the API key in `render.yaml` or Git.

## First deployment checklist

1. Open the Render service logs.
2. Wait until the service reports healthy.
3. Check:

   ```text
   https://YOUR-SERVICE.onrender.com/api/v1/health/ready
   ```

4. Open:

   ```text
   https://YOUR-SERVICE.onrender.com/
   ```

5. Sign in with `ADMIN_EMAIL` and `ADMIN_PASSWORD`.
6. Verify a seller and buyer page load.
7. Upload a test document and verify that it persists after a restart.
8. Confirm private files are not publicly accessible.

The service can take several minutes to build the Docker image on its first
deployment.

## Automatic deployments

`render.yaml` sets:

```yaml
autoDeploy: true
```

After the first Blueprint deployment, pushing to `master` triggers a new
deployment automatically. To deploy another branch, change the branch in the
Render service settings or create a separate Blueprint.

## Updating environment variables

1. Open **Render Dashboard → trustdrive → Environment**.
2. Add or edit the variable.
3. Click **Save Changes**.
4. Choose **Deploy latest commit** or let Render restart the service.

Changing `JWT_SECRET` invalidates existing sessions. Changing the database path
can make the application appear empty because it points at a different SQLite
file. Do not change `TD_DB_FILE`, `TD_DB_URL`, or the disk mount path casually.

## Backups and persistent storage

The `/data` disk contains:

```text
/data/trustdrive/trustdrive.db
/data/trustdrive/trustdrive.db-wal
/data/trustdrive/trustdrive.db-shm
/data/trustdrive/uploads/
/data/trustdrive/quarantine/
/data/trustdrive/langgraph-checkpoints.db
```

The disk persists across normal deploys, but it is not a substitute for
backups. Configure an operational backup process before production use.

## Why not separate Static Site + Backend?

A separate Render Static Site would not run:

- Next.js API routes
- server-side authentication
- database writes
- private document downloads
- upload handling

A separate FastAPI service would also receive a different filesystem, so it
could not safely share the SQLite file or uploaded documents. A split
architecture requires migrating the Next.js data layer to shared Postgres and
moving uploads to shared object storage first. That is a future scale-out
project, not the current deployment path.

## Troubleshooting

### Build fails

Check the Render build logs and confirm the service is using the repository
root, not `frontend/` as the root directory.
`project/infra/docker/Dockerfile.render` needs `frontend/`, `backend/`, and
`services/`.

### Health check fails

Check service logs for:

- Python dependency installation errors
- port `10000` binding errors
- missing `ADMIN_EMAIL` or `ADMIN_PASSWORD`
- inability to write `/data`

The health endpoint is:

```text
/api/v1/health/ready
```

### Login does not work

Confirm `ADMIN_EMAIL` and `ADMIN_PASSWORD` are set in Render Environment and
redeploy. Use `TD_SEED_DEMO=1` only for a demo deployment; a real customer
instance should use `TD_SEED_DEMO=0` so the published demo accounts are not
created.

### OCR upload fails or the service restarts

The combined image runs Next.js, FastAPI and the DB worker in one container.
RapidOCR's ONNX sessions need roughly 250-330 MB of peak headroom, which can
exceed the 512 MB Free plan even after the worker moved inline; the kernel then
kills the service mid-upload. The Free blueprint therefore sets
`TD_OCR_PROVIDER=tesseract`. Tesseract 5 is a real OCR engine that runs as a
short-lived binary with a ~30-60 MB peak, and every result still names the
engine and binary version that ran.

The upload path also enforces `TD_OCR_MIN_FREE_MB` (160 on this blueprint). If
there is not enough free memory, the document is stored and stays `pending`
with an honest reason instead of OOM-killing the service. Check the admin
integration payload:

```text
GET /api/v1/health/integrations  ->  memory, ocrHeadroom
```

Mitigations, in order:

1. Keep `TD_WORKER_MODE=inline` so the worker shares the FastAPI process.
2. Keep `TD_OCR_MAX_IMAGE_SIDE` at `1024` or lower for large phone photos.
3. Keep `TD_OCR_PROVIDER=tesseract` on Free. On Starter (2 GB) you can set
   `TD_OCR_PROVIDER=rapidocr` for higher accuracy on noisy photos; PDFs with a
   real text layer never load an OCR engine.
4. Retry the extraction when the service is idle; the document is not lost.

Verified on commit `f14853e` (12 Nov 2026): a PNG upload returned 201 in 8.5 s
with `engine=tesseract`, `method=tesseract-cli-lstm-5.3.0`, confidence 0.659 and
5 stored fields, while `/api/v1/health/integrations` reported 160 MB required
headroom and ~352-367 MB free. No new `Instance failed` event was recorded.

### Data disappeared

Check that the persistent disk is mounted at `/data` and that these variables
still point there:

```env
TD_DATA_DIR=/data/trustdrive
TD_DB_FILE=/data/trustdrive/trustdrive.db
TD_DB_URL=sqlite+pysqlite:////data/trustdrive/trustdrive.db
TD_UPLOAD_DIR=/data/trustdrive/uploads
```
